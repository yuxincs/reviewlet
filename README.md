# Reviewlet

Reviewlet is a self-service AI code reviewer for ad-hoc snippets. Paste code, find
bugs, and explore the explanation directly in the editor: linked variables,
animated data flows, illustrative values, and suggested changes. No repository
or pull request is required.

## Setup

Requires **Node.js 24 or newer**, npm, **Go 1.27 or newer**, and Make. From the
repository root, one command installs the frontend dependencies, builds both
components, and starts the application:

```sh
OPENAI_API_KEY="your-api-key" sh -c 'npm --prefix frontend ci && make run'
```

Open **http://localhost:8080**. The server prints this URL in bold once it is
listening. Press **Ctrl+C** to shut it down. The first build needs network access
to download dependencies and the pinned API generators.

For subsequent runs, with `OPENAI_API_KEY` already exported, use `make run`.
It rebuilds the production frontend and Go binary, then serves the site and API
from one process in one terminal. The backend reads environment variables
directly; it does **not** load `.env` files automatically.

Click **Try a demo** to add six snippets in TypeScript, JavaScript, Python, Go,
Rust, and Java. The newest, selected example is a 106-line checkout endpoint
with sample cart inputs and expected totals. The smaller examples cover tenant
caching, shipping units, integer arithmetic, stock reservations, and directory
boundaries. Click **Review snippet** or press **Command+Enter / Ctrl+Enter** to
review one. Demo findings are generated by the real backend; they are not
prefilled.

### Configuration

See [`backend/.env.example`](backend/.env.example) for an example configuration.

| Variable                       | Default                     | Purpose                                                    |
| ------------------------------ | --------------------------- | ---------------------------------------------------------- |
| `OPENAI_API_KEY`               | Required                    | Server-side provider credential                            |
| `OPENAI_MODEL`                 | `gpt-6.1-sol`               | Initial findings and fallback guide model                  |
| `OPENAI_DETAIL_MODEL`          | `gpt-6-luna`                | Per-finding explanation model                              |
| `OPENAI_BASE_URL`              | `https://api.openai.com/v1` | OpenAI-compatible Chat Completions endpoint prefix         |
| `REVIEW_TIMEOUT`               | `90s`                       | Overall review deadline                                    |
| `OPENAI_MAX_COMPLETION_TOKENS` | `16384`                     | Per-call completion budget, including reasoning            |
| `LISTEN_ADDR`                  | `:8080`                     | HTTP listen address                                        |
| `DATABASE_PATH`                | `data/reviewlet.db`         | SQLite file, relative to the backend working directory     |
| `LOG_LEVEL`                    | `info`                      | Structured log threshold                                   |
| `FRONTEND_DIST`                | Unset                       | Frontend build directory; `make run` sets it automatically |

With `make run`, the database defaults to `backend/data/reviewlet.db`. It is
created automatically and survives restarts. Credentials stay on the server;
submitted code and review context are sent to the configured model provider.

This prototype has a **single shared workspace without authentication or user
ownership**. Applying fixes is unfinished and disabled by default. Enable
**Apply fix (unfinished)** beside the review button to apply an inline diff;
explanations, suggestions, and diff previews work with the toggle off. AI
conversation with findings is not implemented.

## Architecture overview

```text
Browser: React + TypeScript
  ├─ highlight.js language detection
  └─ Tree-sitter WASM syntax highlighting and review overlays
             │ JSON requests / streamed review snapshots
             ▼
Go HTTP server ───── SQLite: snippets, reviews, decisions
             │
             └───── LLM provider: findings → concurrent detailed guides

api/openapi.yaml → generated Go bindings, validation schemas, and TS client
```

- **React + TypeScript (`frontend/`)** supports quick UI iteration and typed
  rendering of findings, source references, sample values, and edits. Tree-sitter
  runs locally in the browser and handles incomplete code; highlight.js infers
  the language, with a manual override available.
- **Go (`backend/`)** provides a small HTTP server with standard-library
  networking, cancellation, and straightforward concurrency. For evaluations,
  it also serves the built frontend, keeping deployment and local setup simple.
- **OpenAPI (`api/`)** defines the boundary between the two languages. Generated
  clients, server bindings, and runtime validation reduce contract drift without
  tying the frontend to the backend's implementation language.
- **SQLite** makes the single-user prototype persistent without requiring a
  separate database service. Snippet versions and review-run tokens protect
  against stale updates. It is a deliberate setup tradeoff for this prototype.
- **Staged model calls** make findings visible before all explanations are
  ready. A stronger model detects issues; a faster model generates guides in
  parallel. Strict Structured Outputs and source validation make the output
  usable by the editor, while configurable models allow experimentation.

### How a review works

1. The frontend saves the snippet and posts its exact code, language, and context
   to `/api/v1/review`, requesting a server-sent event stream.
2. The primary model returns initial findings. The server assigns stable IDs,
   records the source hash, and publishes the findings immediately.
3. Up to three guide requests run concurrently for that snippet. Each produces
   explanation steps and optional variable links, flows, example values, and
   edits. Rejected output falls back once to the primary model; a failed guide
   retains its finding with an explicit unavailable state.
4. The backend checks source ranges, UTF-16 columns, symbol identities, flow
   edges, and edits, then saves and streams each updated snapshot. The frontend
   updates the selected guide in place. Completed guides remain usable if
   another guide fails.

The editor shows a scanning highlight during detection and animated outlines on
findings awaiting details. Click a finding's line to open its guide; use
**Left/Right** to navigate steps and **Up/Down** to navigate findings. Individual
findings can be dismissed, and an enabled fix can be previewed, applied, and
undone. Applying a fix remaps unaffected finding locations; overlapping changes
are marked for recheck.

Reviews run independently across snippets. You can switch snippets, start another
review, or edit an unrelated draft while requests continue. Progress and errors
stay with their snippet. Leaving the workspace cancels active requests. Saves
occur after five idle seconds and on blur or navigation; the workspace loads once
at startup rather than polling over local edits.

Prompts are embedded in the Go binary from
[`backend/internal/review/prompts/`](backend/internal/review/prompts/). The
application reviews source as text and does not execute submitted snippets or
illustrative inputs. Request IDs correlate structured logs without logging
source, credentials, or provider response bodies.

For contract details, see [`api/openapi.yaml`](api/openapi.yaml). JSON-only
callers can also request a synchronous, single-pass review. Existing latency
experiments and their limitations are recorded in
[`api/review-latency.md`](api/review-latency.md).

## What I'd do differently

With more time, or for a production system, I would prioritize:

1. **A database designed for concurrent service workloads.** Replace SQLite with
   PostgreSQL, design indexes and migrations around actual access patterns, and
   support concurrent writes and multiple backend instances. SQLite was useful
   for making this prototype easy to run.
2. **Multi-user support.** Add authentication, explicit snippet ownership, and
   authorization on every workspace operation. Isolate users' data and introduce
   per-user request and usage limits.
3. **More polished illustrations.** Refine flow routing, highlight placement,
   panel positioning, sample-value placement, and responsive behavior. These
   interactions need more visual iteration, particularly for dense or overlapping
   flows.
4. **Prompt tuning backed by regression benchmarks.** Build a versioned set of
   snippets with known issues and expected explanations. Evaluate finding recall,
   false positives, source/flow accuracy, edit correctness, latency, and cost
   whenever prompts or models change. The current latency probes are a starting
   point, not a comprehensive quality benchmark.
5. **Broader model selection to reduce cost.** After benchmarking, route different
   tasks to suitable models: discovery, explanation, example generation, and
   fallback need not use the same model. Choose combinations based on measured
   quality and cost rather than assuming a cheaper model is sufficient.
6. **Traditional program analysis for symbol resolution.** Use compiler,
   language-server, or static-analysis results for bindings and data-flow
   relationships where available. This could reduce expensive model-generated
   bookkeeping and improve reference accuracy, with a fallback for partial or
   unsupported snippets.
7. **Better explanation steps.** Tune how steps are grouped, ordered, and focused.
   Select example inputs and intermediate values that make the failure easy to
   understand, and evaluate whether each step adds useful information instead of
   merely repeating the finding.

## AI Usage Log

**Coding tool used: Codex.** I used it throughout development for prototyping,
implementation, and iteration. The examples below describe my development
workflow; the application's runtime use of LLMs is described above.

### Specific examples

1. **Prototyping before building the full system.** Codex helped me turn an idea
   into a working frontend quickly. I initially used entirely mocked backend
   responses to experiment with the editor, findings, and review guides. This
   let me validate the interaction without paying model costs or waiting for
   live requests on every iteration. I connected the real backend after the
   workflow was worth pursuing.
2. **Overriding unnecessary work.** Codex sometimes tried to anticipate what I
   wanted and overcomplicated the process. For example, it repeatedly ran the
   full check suite after individual feature changes, which slowed iteration.
   I had to give it explicit rules about when substantial changes warranted
   testing and when focused verification was enough. The pre-push hook runs the
   complete suite to catch issues before changes are pushed.
3. **Working in less familiar languages and frameworks.** Implementing the
   React/TypeScript frontend myself would have taken considerably longer.
   Codex wrote most of that code, including the editor interactions, floating
   review panel, keyboard navigation, and visualizations. I could concentrate
   on the experience I wanted, inspect the result, and ask for changes where
   the generated interface did not match that intent.

### Overall impression

Codex sped me up significantly. Building a system like this within a few hours
would otherwise have been difficult. It also made experimentation much cheaper:
I could try several interface ideas, see how they felt, and discard or revise
an approach without worrying as much about wasted engineering effort. Separate
worktrees also let me explore ideas concurrently.

The main slowdown was supervising decisions I had not asked it to make. It
sometimes inferred extra requirements, added complexity, or spent too much time
on verification during small iterations. I spent time adding skills, rules, and
guardrails so it would stay within the intended scope. My judgment was still
needed to decide what to build, which results to keep, and where the generated
code or UX needed another pass.

## Development and checks

For hot reload, run the backend and Vite in separate terminals after installing
frontend dependencies:

```sh
# Terminal 1, repository root; OPENAI_API_KEY must be exported
make backend-run

# Terminal 2, repository root
npm --prefix frontend run dev
```

Vite proxies `/api` to `http://localhost:8080`. The backend serves only the API
when `FRONTEND_DIST` is unset.

```sh
make generate              # Regenerate Go bindings, schemas, and TS client
make build                 # Build frontend and backend
make frontend-check        # Frontend lint, format, tests, and production build
make backend-check         # Backend lint, format, and tests
make check                 # Full suite; no external LLM calls required
make install-hooks         # Enable the full-suite pre-push hook
```

The generators are pinned: `oapi-codegen` v2.8.0 through Go's tool dependencies
and Hey API v0.99.0 through npm. Generated code is ignored by Git and regenerated
by the Make targets and frontend scripts; edit the OpenAPI source instead.
Backend linting uses the version in [`.golangciversion`](.golangciversion),
automatically installed with curl when needed. Direct Go commands do not generate
bindings; use Make or run `go generate ./internal/api` first.

The pre-push hook runs the full suite and blocks a failing push. GitHub Actions
runs the frontend and backend checks separately based on changed paths. Live
model benchmarks require explicit opt-in; ordinary tests use local fake providers.
